# 项目复盘笔记：个人 AI 知识库

> 技术复盘：从零搭建一个基于 RAG（检索增强生成）的本地个人知识库 Web 应用。
> 本文所有描述均对照当前代码（`app.py` / `agent.py` / `eval.py` / `ingest.py`），
> 确保与实现一致——面试被问到细节时，以代码为准。

---

## 项目概述

解决一个真实痛点：**网上收藏了无数好文章，却从未真正消化**。

本项目用 RAG 把个人资料（学习笔记、课程 PDF、技术文章）变成"能对话的知识库"——用户提问时，AI **只基于用户提供的资料**给出回答，并标注每段回答的出处来源，而不是凭空编造。

技术亮点：
- **完全本地向量化**：中文 embedding 模型（`bge-small-zh-v1.5`）在本机运行，资料不出本机，隐私可控。
- **生产级检索链路**：递归切分 → 句向量化 → Chroma 向量库 → 两阶段检索（向量召回 + ReRank 重排）→ 大模型生成。
- **可见的溯源**：每个回答都标注「文件名#片段序号」，方便核对，降低幻觉。
- **手写 Agent**：`agent.py` 手写 ReAct 循环（不依赖框架），并额外用 LangGraph 重写了一版对照实现（`langgraph_agent.py`）。

---

## 技术选型

| 环节 | 选型 | 取舍理由 |
|------|------|---------|
| Web 框架 | **Flask** | 轻量、易讲清请求/响应全链路，比 Streamlit 更"正经" |
| 中文向量化 | **sentence-transformers + BAAI/bge-small-zh-v1.5** | 本地运行，中文检索效果好，免费 |
| 向量库 | **Chroma (chromadb)** | 本地持久化，几行代码即可上手 |
| 生成模型 | **智谱 GLM-4-flash** API | 有免费额度，OpenAI 兼容协议 |
| 重排模型 | **BAAI/bge-reranker-base**（交叉编码器，可选） | 二阶段精排，Top-3 命中率从纯向量检索的 94.4% 提升到接近 100% |
| 文档解析 | **pdfplumber** + **python-docx** + 原生 `.md/.txt` 读取 | 支持 PDF / Word / 文本 |
| 文本切分 | 手写递归切分（带重叠窗口） | 自己实现，原理清晰、可控 |

## RAG 链路实现

```
上传文件
  → 解析为纯文本（pdfplumber / python-docx / 直接读取）
  → 递归切分为带重叠的片段（默认 500 字 / 重叠 80 字）
  → sentence-transformers 生成句向量
  → 存入 Chroma 向量库（持久化到 chroma_db/）
        │
提问
  → 问题向量化
  → 第一阶段：Chroma 向量召回 Top-10 候选
  → 第二阶段：bge-reranker-base 交叉编码器精排 → 取 Top-3
  → 拼接为带【资料】标记的 Prompt（含对话历史压缩）
  → 智谱 GLM-4-flash 生成回答
  → 返回回答 + 来源引用（文件名#片段序号）
```

关键点：
- 检索结果通过 `metadata` 携带 `source`（来源文件名）与 `chunk`（片段序号），回答时回传给前端展示，做到可溯源。
- **两阶段检索**：第一阶段向量召回多召回一些候选（给 ReRank 留空间），第二阶段用交叉编码器对"问题-片段"打分重排。ReRank 模型缺失或推理失败会自动降级为纯向量检索，**不影响可用性**。

## 两个真实踩坑与解决

### 1. 国内网络拉不到 HuggingFace 模型
**现象**：`sentence-transformers` 首次加载默认从 `huggingface.co` 下载模型，国内网络经常超时。
**解决**：改用 ModelScope 源把 `BAAI/bge-small-zh-v1.5` 下载到本地 `./models/`，并设置离线环境变量：
```bash
pip install modelscope
modelscope download --model BAAI/bge-small-zh-v1.5 --local_dir ./models/bge-small-zh-v1.5
# 运行时锁定离线，彻底不依赖外网
export HF_HUB_OFFLINE=1
export TRANSFORMERS_OFFLINE=1
```
**收获**：模型变为本地资产，环境可复现、部署更稳。

### 2. 重建知识库后查询拿到"失效集合"（对象生命周期问题）
**现象**：上传文件触发"删除旧集合 → 重建新集合"（`reingest()`）后，一提问就报 `Collection [...] does not exist` 或查到空结果。
**根因与两层修复**：
- **第一层（工具层，关键）**：`build_tools(embedder, get_collection)` 传入的是**函数** `lambda: collection`，而不是 collection 对象。工具每次调用都重新 `get_collection()` 取最新句柄，因此重建后永远不会拿着失效的旧对象查询。
- **第二层（全局句柄）**：`reingest()` 重建集合后，仍把全局 `collection` 重新指向新集合（`global collection; collection = coll`），作为兜底。
> 早期版本只用 `global collection = coll` 这一种修法，一旦工具在模块加载时就把旧对象捕获进闭包，仍会失效。**用"传函数而非对象"才是根治**——这也是为什么 `agent.py` 的注释明确写"框架会把循环藏在黑盒里，手写才能讲清这种细节"。

**另一个相关真坑（已修）**：自动建库逻辑原本写在文件前部，执行时 `reingest()` 尚未定义会抛 `NameError`，又被 `except` 静默吞掉，导致"首次启动自动建库"从未真正生效、新 clone 的项目知识库一直是空的。修复方式是把自动建库挪到 `reingest` 定义之后。

## 关键技术决策（自问自答）

**Q：为什么用 RAG，而不是直接问大模型？**
A：大模型不知道用户的私有资料。RAG 让模型"先检索再回答"，既用上私有知识，又能溯源、降低幻觉。

**Q：chunk 切多大合适？为什么带重叠？**
A：太大检索不精准，太小丢上下文。默认 500 字、重叠 80 字——重叠避免一句话被切断在边界，保证语义完整。

**Q：embedding 为什么用本地模型而不是 API？**
A：一是隐私（资料不出本机），二是成本（本地免费、可离线），三是更可控。线上大批量时也可换 API 版。

**Q：为什么做两阶段检索（向量 + ReRank）？**
A：纯向量召回 Top-3 约 94.4%、Top-1 约 88.9%（见 `eval.py`，小样本自测）；加 ReRank 交叉编码器精排后 Top-3 接近 100%。ReRank 缺失时自动降级，兼顾效果与可用性。

**Q：手写 ReAct 为什么不用框架？**
A：`agent.py` 全部手写，每一步（循环、解析、执行、强制收尾）都看得见，是面试讲清细节的前提；同时保留 `langgraph_agent.py` 作为框架版对照，理解"框架替换了哪一层"。

**Q：这个项目的典型落地价值是什么？**
A：AI 应用开发的核心是把大模型"接进真实业务 + 管好私有数据 + 控住成本与准确性"，RAG 是最典型的落地形态，本项目把这条链路完整走了一遍。

## 评估与工程化

- **检索评估**：`eval.py` 无需 API key 即可跑，从每篇文档抽代表句作 query，测 Top-1 / Top-3 命中率与平均延迟（约 10.6ms）。当前数据是**基于 3 篇文档的小样本自测**，扩库后需重新评估，并计划固化为回归测试基线。
- **部署**：Docker + docker-compose + gunicorn；提供 `/health` 健康检查供 PaaS 探活；ReRank 模型后台线程下载（设 `AUTO_DOWNLOAD_RERANKER=1`），避免阻塞 gunicorn 启动导致部署超时。
- **健壮性**：所有 JSON 响应绕过 Flask `jsonify`，用 `json_response()` 显式 `ensure_ascii=False` + UTF-8，彻底规避 ASCII codec 错误；全局异常兜底返回安全 JSON。
- **反馈闭环（待深化）**：`/feedback` 已能存 👍/👎 到 `feedback.json`，但目前仅记录、尚未用于自动改进检索——这是"自进化体系"的下一步种子。
